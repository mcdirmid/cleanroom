# benchmark_impl implementation component

imports: model_config_ext, app_info_ext
implements: benchmark

## Purpose

The benchmark_impl implementation component realizes empirical benchmark execution, multi-harness dispatch, telemetry log harvesting, two-pass verification gates, and comparative report formatting.

Autonomous model benchmarking requires executing isolated flights across local hardware engines and cloud API harnesses, extracting precise token usage and step latencies from execution logs, running deterministic static and runtime verification gates, and producing publication-ready JSON traces and summary tables. The benchmark_impl implementation component provides concrete adapters for local runtime endpoints, external subagent harnesses, and simulated flights, parsing round and step logs to harvest token and timing metrics, running linters and test suites, and formatting structured markdown and JSON outputs.

**Out of scope:** The benchmark_impl implementation component does not modify source files or provision physical workspace permissions; these are handled by other components.

**Delegated:** Reading declarative model configuration files and rate card schemas is delegated to model_config_ext; user configuration directory resolution is delegated to app_info_ext.

## Types and Behavior

A system's *benchmark evaluator* realizes model efficiency evaluation and verification report generation as a system service.

The benchmark evaluator maintains a model catalog mapping model keys to model specifications loaded dynamically from declarative configuration files across local, budget, mid-tier, and frontier capability tiers, and a suite catalog discovered from the benchmark parts directory mapping each constituent part directory name to a benchmark unit suite.

The benchmark evaluator provides access to the active model catalog mapping model identifiers and aliases to model specifications.

The benchmark evaluator executes a benchmark flight for a designated model specification and benchmark unit under a selected research question tag and harness mode, capturing wall clock elapsed time and generating a unique flight identifier and ISO timestamp. To support concurrent benchmark execution without cross-flight contamination, the evaluator provisions a concise sequential ephemeral flight scope directory under the benchmark runs container (e.g. `benchmarks/runs/<suite>_<model_slug>_<index>`, deriving `<suite>` from the benchmark unit, `<model_slug>` by normalizing the model identifier into a valid identifier, and allocating the next unique sequential index or reusing a completed flight scope slot), preserving the package structure of the benchmark unit's enclosing scope (copying scope configuration and the target unit into `<flight_scope_dir>/parts/<unit>`, explicitly configuring the flight scope's methodology pipeline as `pipeline = "pretense"` when Pretense evaluation is requested, `pipeline = "combined"` when combined evaluation is requested, or `pipeline = "standard"` when standard evaluation is executed, rewriting benchmark imports across copied sources to reference the flight scope package while disallowing bare parts imports, ensuring role workspaces derive dynamically as `<repo_name>_<role_name>_<sanitized_scope>`). When starting a new benchmark run that reuses an existing flight scope slot (or allocating a fresh slot), the evaluator purges any orphaned role workspaces associated with that slot and deletes all existing conversations matching `[<flight_scope>]` from DeepSeek Harness. When executing under an asynchronous subagent harness, the evaluator emits the coordination directive, supports native platform IPC dispatch via `agentapi` or active flight state persistence, and monitors clean convergence across the flight scope until completion or timeout before evaluating verification gates and archiving artifacts, failing fast if the Antigravity harness is selected outside of an active Antigravity environment (`ANTIGRAVITY_AGENT` not detected). When executing under a headless or local harness (such as `dsh`), the evaluator announces headless coordination initiation, streams real-time execution progress to standard output without in-memory output blocking, and awaits completion. Default execution timeouts derive dynamically from the active model configuration catalog (`run_timeout_seconds` in `model_configs.toml`) when an explicit timeout is not passed on the command line. When executing a baseline flight, the evaluator routes execution through the unified Autofab orchestrator and coordinator by targeting the designated fused role (`combined_baseline` when combined methodology is requested, `pretense_baseline` when pretense is requested, or `baseline` otherwise) with relaxed intra-fuse prerequisites, verifying and harvesting all constituent units across the fused role without custom non-fused developer code paths or uncontracted flight scope symlinking, records the methodology as `combined_baseline` (or `pretense_baseline`, or `baseline`), archives passing artifacts under `<model>+<harness>-combined-baseline` (or `<model>+<harness>-pretense-baseline`, or `<model>+<harness>-baseline`), and records one execution round under the baseline role.

The benchmark evaluator harvests flight telemetry by parsing round and step log files modified after flight commencement or subagent session transcripts from an active subagent harness environment. For Autofab subagent harness flights, the evaluator identifies the coordinator conversation (explicitly excluding individual role worker conversations and parent caller sessions that merely emit dispatch directives) and its child role worker conversations, extracting non-cached inbound tokens, cached inbound tokens, outbound tokens, and step duration latencies from planner response entries across all participant conversations, while tallying role execution rounds exclusively across target role workers based on dispatch waves and excluding the coordinator session from role rounds. For baseline flights, the evaluator identifies the baseline developer subagent conversation (rather than a parent caller session that dispatched it) and extracts non-cached inbound tokens, cached inbound tokens (supporting both `cache_read_tokens` and `cached_tokens` transcript fields), outbound tokens, and step latencies from the single baseline developer conversation or log, recording exactly one execution round under the baseline role. The evaluator computes total tokens and financial cost using the model specification's rate card.

The benchmark evaluator evaluates verification outcomes by executing two-pass verification gates against the target benchmark unit directory within the active flight scope, assessing specification linters, static type checks, unit test results, statement coverage, and mutation testing scores. When pretense evaluation is requested, the verification gate executes Pretense test verification (`uv run pretense <unit_dir>/pretense --no-fuzz --cov`) to evaluate deterministic unit tests and statement coverage, assesses property fuzzing passes, and evaluates Pretense verification outcomes. When combined evaluation is requested, the verification gate executes static type checks across library, test, and pretense directories, executes standard unit tests with pytest, and executes Pretense test verification, combining test counts, assertion outcomes, and coverage measurements. The verification gate dynamically resolves constituent package and runtime support paths relative to the active repository root into the execution environment and test runner search path so that inter-module imports and lifecycle support libraries resolve cleanly without hardcoded directory paths.

When simulated execution is requested, the benchmark evaluator produces synthetic telemetry scaled to the benchmark unit archetype size and marks verification gates as passing, recording a single baseline execution round for baseline flights.

The benchmark evaluator serializes each flight trace to a structured JSON file matching the canonical schema under a benchmark logs directory.

The benchmark evaluator formats flight traces into a markdown summary report presenting model tiers, status indicators (marking passing flights as PASS and failed flights as FAILED with defect diagnostics), token metrics, financial costs, wall clock durations, and verification outcomes, saving the report to a designated output path when provided.

The benchmark evaluator archives synthesized library, test, and Autofab event log files produced by the model into a results directory structured by benchmark identifier and model identifier (`benchmarks/results/<benchmark-id>/<model-name>/`, appending `-combined` when combined methodology is requested, `-pretense` when pretense is requested, `-baseline` for baseline flights, `-combined-baseline` / `-pretense-baseline` when combined with baseline, and `-[experiment]` when an active experiment is configured, defaulting to `structured_blame` for non-baseline flights unless explicitly disabled) exclusively for successful flights that pass verification gates (zero unit test failures, at least one passing unit test, zero type errors, passing specification linters, and clean DAG convergence with exit code zero). When dry-run mode is active or when a flight fails verification gates or fails to materialize synthesized library or test files, the evaluator skips artifact archival. For multi-file library implementations in successful flights, the evaluator preserves all constituent non-dunder implementation files within `lib_<N>.py`. The evaluator determines the next available sequential run index, writes the library file as `lib_<N>.py` with a header comment capturing flight telemetry metrics, financial cost, wall-clock duration, role execution rounds, and verification outcomes, writes the test or pretense file as `test_<N>.py` or `pretense_<N>.py` (preserving both `test_<N>.py` and `pretense_<N>.py` when combined methodology is requested), and, when present, copies the Autofab event log from the flight scope as `autofab_<N>.log`.

The benchmark evaluator drains pre-existing library and test files from the target benchmark unit directory within the flight scope before executing a flight (including `lib/`, `tests/`, `pretense/`), cleans up orphaned flight scope directories and associated role workspaces from prior flights, marks specifications clean up to specification QA within the flight scope (synchronizing in-band specification metadata and running `autofab mark-clean <flight_unit> --up-to-role spec_qa`) to ensure only library implementation, unit tests (or pretense suites), and QA verification are evaluated, and concludes the flight scope lifecycle after flight completion and archival. Rather than deleting the flight scope directory or moving failed flights to `.failed` directories upon flight completion, the evaluator marks completion metadata within the flight scope directory and in associated role workspaces (writing `flight_status.json` recording flight identifier, scope, status as `finished` for passing flights or `failed` for failed flights, verification outcome, and completion timestamp), preserving the flight scope working tree and role workspaces on disk in-place so that session navigation and workspace inspection in external harnesses (such as DeepSeek Harness Web) remain fully operational without crashing. When recycling slots for subsequent benchmark runs of the same suite and model, only slots marked with status `finished` are automatically recycled; slots marked with status `failed` are preserved for troubleshooting and inspection and are never automatically overwritten, causing subsequent runs to advance to the next sequential index until failed runs are explicitly cleaned up.

The benchmark evaluator processes command-line arguments to resolve a single target model per flight via `--model` (or `--models`, strictly rejecting comma-separated model lists to prohibit multi-model sequential execution), benchmark suites (using part directory names from benchmark parts or all discovered suites), tier filters, research question tags, unit count limits, harvest flight identifiers, baseline evaluation flags (disallowing the loop harness), methodology options (`--method` accepting `standard`, `pretense`, or `combined`, with `--standard`, `--pretense`, and `--combined` as non-deprecated CLI aliases), active experiment options (`--experiment <name>`, defaulting to `structured_blame` for non-baseline flights unless disabled via `--disable_experiment <name>` or `--no-experiment`, strictly configuring active experiments and appending the experiment identifier suffix to results archival), and execution modes (`--dsh-web` for DeepSeek Harness Web loopback bridge execution, or `--dsh-desktop` to explicitly force DeepSeek Harness Desktop RPC execution even when Web mode is the configured default), executing the resolved benchmark matrix and reporting results, returning exit code 0 when all flights pass verification or 1 when any flight fails verification or execution.
