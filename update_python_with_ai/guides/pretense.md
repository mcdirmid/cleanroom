# Guide: Pretense State Machine and Test Author

## Summary

The artifact is a Pretense test and fake synthesis module (`pretense/<name>_pretense.py`) that models and tests `lib/<name>.py` per `low/<name>.pyi`, submitted via `submit(target="<target_file>", change_summary="...")`. In multi-node sessions, multiple targets are processed together by package-relative alias path. When starting from a template or missing artifact, pretense scaffolding (`uv run python -m update_python_with_ai.support.lib.pretense_lint --scaffold <target> --pyi low/<name>.pyi --impl lib/<name>.py`) generates a canonical 5-section skeleton with model state, transitions, fake synthesis, unit tests, and property fuzzing. Cleanroom metadata blocks at the bottom of the file (under `# --- CLEANROOM METADATA ---` and `# --- END CLEANROOM METADATA ---`) are managed automatically by Cleanroom tooling upon `submit(change_summary=...)`; direct edits to metadata blocks are prohibited and rejected by editing tools. All operations and state assertions derive directly from contractual invariants (`INVARIANTS:`) and operational postconditions (`POSTCONDITIONS:`) in `low/<name>.pyi` across the transitive inheritance hierarchy. Only singletons and data types can be tested; poly types without singletons have nothing to test and are instantiated only to supply collaborator instances needed by singletons.

The pretense module consolidates state modeling, fake generation, unit tests, parity verification, and stateful fuzzing into a single cohesive module containing five canonical sections. Section 1 defines a dataclass representing the model state (`<Target>State`) alongside a state machine class (`class <Target>StateMachine(StateMachine[<Target>State])`) defining atomic transitions decorated with `@transition(TargetClass.method)` accepting `ctx: TransitionContext[TargetClass, [arg_types...], ret_type]` to bind requires preconditions, argument binders, return outcomes, ensures postconditions verified against real singletons under test, and update state mutations (or legacy prototype transitions using `StateMachineProto[<Target>State]()`). State machine Fakes act strictly as lightweight specification oracles modeling preconditions, abstract state mutations, and functional return outcomes; they never instantiate target service classes, never invoke runtime singletons (`get_singleton`), and never implement complex combinatorial algorithmic search (backtracking solvers, SAT engines). Functional operations, parsing queries, and comparison contracts (`parse_version`, `compare_precedence`, `satisfies`) must be modeled accurately in the state machine or pure top-level reference helper functions (e.g. `_ref_precedence`, `_ref_parse_version`), returning exact computed outcomes rather than static dummy values (`0`, `True`, or fixed instances). Algorithmic stress-testing of combinatorial solving belongs in granular, single-concept test methods in `Test<Target>ImplReal`. Caller assumptions (`ASSUMPTIONS:`) and static type contracts define caller preconditions accepted axiomatically; authoring negative tests or asserting uncontracted non-concerns is prohibited. Section 2 defines the state machine instance and fake factory functions returning synthesized in-memory fakes (`sm.as_fake(TargetClass)`). Section 3 defines deterministic unit tests (`Test<Target>Unit`) inheriting from `unittest.TestCase` asserting that synthesized fakes execute valid state transitions and raise contracted exceptions on error conditions. Section 4 defines concrete implementation tests (`Test<Target>ImplReal`) executing real library classes within isolated test lifecycle registries, asserting full behavioral parity against the state model and achieving 100% statement coverage of the companion library implementation under `--no-fuzz --cov`. Behavioral assertions and operational postconditions belong exclusively in transition `ensures` blocks evaluated automatically on every transition during real test and fuzz runs; test methods in `Test<Target>ImplReal` drive operational scenarios by dispatching transitions through `self.sm.dispatch_transition(...)` with zero manual outcome assertions (`assertEqual`, `assertTrue`, `assertFalse`), reserving manual assertions strictly for `assertRaises` on contracted error branches. Transition `ensures` blocks must verify general invariants across all valid inputs, never hardcoding sample-specific literal constants or fixed return values. Section 5 defines Hypothesis stateful property tests (`Test<Target>Fuzz` or `compile_hypothesis_test_case`) verifying equivalence invariants, ensures postconditions, and absence of uncaught crashes across arbitrary interaction sequences. Time-dependent operations use fast sub-second durations (`0.01` to `0.05`s) or mock time progression rather than wall-clock delays. When addressing verification feedback or blame reports from downstream roles, all sibling transitions, methods, and test assertions in the module must be audited for the same failure pattern before submitting, preventing narrow single-defect patches and multi-round ping-pong loops. Conversational commentary without tool execution is prohibited; execution proceeds continuously via tool calls until the round concludes with `submit` or `fail`.

> META: "Pretense modules model interface state transitions, synthesize in-memory fakes, verify concrete implementations with full coverage, and execute bounded property fuzzing."

## Guide structure

- [ ] File contains five sections in order: Model State & Transitions, State Machine Proto & Fakes, Fake Unit Tests, Real Implementation Tests, and Hypothesis Fuzzing
- [ ] Imports include standard typing tools, `unittest`, `hypothesis`, `pretense.proto`, `pretense.sentinels`, `support.lib.lifecycle`, and the target library classes
- [ ] Cleanroom metadata comments at the bottom of the file are preserved without manual edits
- [ ] No conversational text or commentary is emitted without accompanying tool execution

## Lint checks

- [ ] Module defines at least one dataclass whose name ends with `State` representing model state
- [ ] Module defines at least one `unittest.TestCase` subclass or compiled Hypothesis test case
- [ ] Module imports `StateMachine` (or `StateMachineProto`), `transition`, and `TransitionContext` (or `Raised`, `Value`)
- [ ] Module imports target classes and initialization functions directly from the companion library implementation
- [ ] Module contains valid Python syntax and passes Pyright type checking with zero errors
- [ ] Module imports public specification symbols and lifecycle hooks; importing private `_*` functions or implementation internals from library modules is prohibited
- [ ] Test methods in `Test<Target>Unit` and `Test<Target>ImplReal` contain meaningful assertions on behavior, state transitions, or return values; tautological assertions (e.g. `assertTrue(True)`, `assertEqual(1, 1)`) and empty test methods are prohibited
- [ ] Transitions never return or assign residual sentinel stubs (`NotBound`) in `ctx.returns(...)` or returns handlers; test assertions never assert equality against `NotBound`
- [ ] Multiple transitions targeting the same interface method on a state machine declare distinct model preconditions via `ctx.requires(...)` or discriminative input domains via `ctx.arguments(...)` to prevent `AmbiguousTransitionError` during Fake dispatch
- [ ] State machine classes never instantiate target service classes under test or invoke `get_singleton`; state machines operate purely on abstract model state (`self.state`)
- [ ] State machine methods never define nested algorithmic functions (such as `backtrack`, `solve`, or `search`) or while loops within transitions
- [ ] Test modules never tamper with, delete from, or clear `sys.modules`; runtime harness isolation and module reloading are managed exclusively by Cleanroom harnesses
- [ ] Module contains zero residual scaffolding crash placeholders (`_unimplemented_transition`, `Domain.required`, placeholder `check(False, ...)`, or scaffold `self.fail`); leaving placeholder stubs in transitions or tests is strictly prohibited and rejected by verification
- [ ] Scaffolding command `uv run python -m update_python_with_ai.support.lib.pretense_lint --scaffold` generates a skeleton where unspecialized returns, domains, and assertions crash at runtime with `NotImplementedError` or `AssertionError` if left unimplemented, preventing deceptive passes

## State modeling and transitions

- [ ] Model state is declared as a dataclass ending with `State` (e.g. `<Target>State`), storing state collections and tracking flags
- [ ] Collections within model state use standard containers (`list`, `dict`, `set`) or Pretense observable collections
- [ ] State machine is declared as a subclass of `StateMachine[<Target>State]` (or initialized as `proto = StateMachineProto[<Target>State]()`)
- [ ] Each public method across all target interfaces has an associated `@transition(TargetClass.method)` transition definition method accepting `ctx: TransitionContext[TargetClass, [arg_types...], ret_type]`
- [ ] Transition methods declare preconditions via `ctx.requires(lambda check: check(...))` checking model state preconditions without exception overhead (or legacy `ctx.antecedent`)
- [ ] Transition methods declare argument domains via `ctx.arguments(...)`:
  - **Standard Domains**: Pass declarative `Domain` objects or native Python primitives (`Domain.range(0, 100)` or `range(0, 100)`, `Domain.set(...)` or `{"a", "b"}`, `Domain.regex(r"...")` or `re.compile(...)`, `Domain.boolean()`).
  - **Dependent & Relational Domains**: When an argument depends on a prior argument, pass a callable closure `arg_N=lambda arg_1: Domain...`; for relational comparisons or near-boundary transitions, use `Domain.perturb(anchor, mutations=[...], validator=...)` with small constructive deltas (+1, -1) rather than attempting to write an algorithmic constraint solver; ensure the validator recognizes the union of all declared mutation paths.
  - **Multi-Value Edge-Case Pools**: When custom domains are needed and general random generation is impractical, sample across a discrete multi-value pool covering critical boundaries (zero, max, empty, non-empty, special characters). Hardcoding static single-sample dummy values (e.g. `lambda: ("1.0.0",)` or `"sample_name"`) or leaving `Domain.required(...)` or unconstrained `Domain.type(T)` as a dummy placeholder is strictly prohibited and crashes at runtime.
  - **Strict Prohibition on Domain Widening**: When argument recognition fails during `dispatch_transition` (e.g. `Argument generation/recognition failed for '<transition>'`), widening the domain to raw unconstrained types (`Domain.type(str)`, `Domain.type(int)`, or raw class types without validators) as an error escape hatch is strictly prohibited. The author must expand the domain sample pool (`Domain.set([...])` or regex) to explicitly include all valid values dispatched in test scenarios, or author a constructive domain generator.
- [ ] Transition methods declare expected outcomes via `ctx.returns(lambda ...: ...)` or contracted exceptions via `ctx.raises(ExpectedException, match="...")`; declaring both `ctx.raises` and `ctx.returns` on the same transition context is strictly prohibited and raises a `ValueError`; hardcoding dummy static return constants (such as returning `0`, `True`, or static dummy instances for dynamic operations) or leaving `_unimplemented_transition(...)` stubs is strictly prohibited and crashes at runtime with `NotImplementedError`; for methods with conditional error branches, model separate transitions or return `Raised(ExpectedException(...))` dynamically from `ctx.returns`
- [ ] Transition methods declare postconditions via `ctx.ensures(lambda res, target, check, *args: ...)` asserting operational postconditions and invariants on the concrete singleton under test during real test and fuzz execution (`check(condition, msg)` and `check.equal(actual, expected)`); collaborating singletons are retrieved via `check.get(OtherSingleton)`; ensures verification is omitted during fake adapter execution
- [ ] Transition `ctx.ensures(...)` postconditions verify general invariants across all valid inputs; hardcoding sample-specific literal constants or fixed return values (such as `check.equal(res, True)`, `check(res < 0)`, or `check.equal(res, {})`) into `ctx.ensures` is strictly prohibited
- [ ] Prohibition on type-only and tautological ensures: `ctx.ensures(...)` must never consist solely of type checks (`isinstance`) or unconstrained ranges (`res in (-1, 0, 1) or res < 0 or res > 0`); for pure computational queries, formatting, or comparisons, `ensures` verifies outputs against state machine reference oracles (`check.equal(res, expected)`) or mathematical invariants (antisymmetry, transitivity, bounds)
- [ ] For predicate queries, `ctx.ensures(...)` verifies boolean correctness across both positive and negative scenarios against model state or oracles, never asserting that the outcome is unconditionally `True`
- [ ] For search or solver operations, `ctx.ensures(...)` verifies structural invariants (such as input constraint satisfaction across selected elements) rather than asserting an empty collection or unconstrained type check
- [ ] Exception classes are never decorated with `@dataclass(frozen=True)` because Python exception handling and traceback mechanisms assign `__traceback__` on exception instances
- [ ] Transition methods declare state mutations via `ctx.update(lambda res, ...: ...)` updating backing model state (or legacy `ctx.consequent`)
- [ ] Multiple discrete transitions for the same target method (such as success vs error, valid vs invalid input, or distinct lifecycle states) are supported; when synthesizing Fakes, candidate transitions for the same target method must declare mutually exclusive `ctx.requires(...)` conditions or discriminative `Domain` validators via `ctx.arguments(...)` so that Fake adapter dispatch identifies exactly one matching transition without `AmbiguousTransitionError`
- [ ] Transition return handlers return concrete result values, state expressions, or `Raised(...)` exceptions; returning un-instantiated sentinel stubs (`NotBound`) is strictly prohibited
- [ ] Transition argument and return handlers for entity creation or addition (such as `add_node`) do not perform eager validation of referenced entities unless explicitly specified; validation belongs in explicit validation operations (`validate`) when specified
- [ ] Transition return handlers for non-deterministic fields (such as elapsed wall-clock durations or random tokens) match outcome types or structural shapes rather than asserting fixed constant values
- [ ] In composite state machines with multiple interconnected services, entity lifecycle creation or addition transitions (such as adding nodes or tasks) initialize corresponding lifecycle tracking states across all constituent sub-states in consequents (e.g. initializing new nodes into scheduler state as ready or pending)
- [ ] State machine methods, transitions, and consequents operate purely on abstract model state (`self.state`); instantiating target service classes under test, accessing live runtime singletons, or invoking `get_singleton(...)` is strictly prohibited
- [ ] State machine transitions never implement complex algorithmic solving (such as recursive backtracking, SAT solvers, or parsing engines); transition return handlers return canonical state-derived values or synthesized data types
- [ ] Caller assumptions (`ASSUMPTIONS:`) in specifications are accepted axiomatically; modeling assumption violations is prohibited

## Fake synthesis and unit tests

- [ ] Synthesized fake is created via `proto.make_state_machine(state).as_fake(TargetClass)` or an explicit fake factory function `make_<name>_fake`
- [ ] For modules with multiple service classes sharing model state, fake factory `make_<name>_fakes` synthesizes a tuple of fakes backed by one shared `StateMachineProto` instance
- [ ] Fake unit tests inherit from `unittest.TestCase` under class name `Test<Target>Unit`
- [ ] `setUp` initializes a fresh model state instance and state machine fake for each test method
- [ ] In `Test<Target>Unit` for multi-service modules, `setUp` unpacks synthesized fakes into distinct instance attributes (e.g. `self.dag`, `self.scheduler`, `self.runner`)
- [ ] Test methods verify each transition through the fake, asserting returned values match expected state outcomes
- [ ] Test methods verify that invalid inputs or error preconditions trigger contracted exceptions wrapped in `Raised`
- [ ] Test assertions verify that mutator operations update the backing model state correctly

## Implementation verification and parity

- [ ] Real implementation tests inherit from `unittest.TestCase` under class name `Test<Target>ImplReal`
- [ ] For lifecycle-managed components declaring a tier, `setUp` initializes an isolated `LifecycleRegistry`, calls `__initialize__(self.registry)`, enters `self.phase_scope = enter_phase(system, registry=self.registry)`, and binds resolved target singletons into a real-mode state machine instance `self.sm = TargetStateMachine(singletons={...})`
- [ ] For non-lifecycle components, `setUp` instantiates the real target classes and binds them into `self.sm = TargetStateMachine(singletons={...})`
- [ ] In `Test<Target>ImplReal`, `tearDown` exits the phase scope via `self.phase_scope.__exit__(None, None, None)` for lifecycle-managed suites
- [ ] Test methods in `Test<Target>ImplReal` drive operational scenarios primarily by dispatching transitions through `self.sm.dispatch_transition("<transition_name>", *args)` to achieve 100% statement coverage under `--no-fuzz --cov`
- [ ] Operational postconditions, return outcomes, and state invariants are verified automatically by transition `ctx.ensures(...)` handlers on every dispatched transition; fixed scenario test methods in `Test<Target>ImplReal` contain zero manual return-value assertions (`self.assertEqual`, `self.assertTrue`, `self.assertFalse`, `self.assertLess`, `self.assertGreater`), driving operational scenarios exclusively through `self.sm.dispatch_transition(...)` and reserving `self.assertRaises(...)` strictly for contracted exception verification on invalid inputs or error conditions
- [ ] Bypassing state machine dispatch to invoke target singleton methods directly with manual return-value assertions in `Test<Target>ImplReal` is strictly prohibited
- [ ] Duplicate manual assertions across `Test<Target>ImplReal` for conditions already guaranteed by `ctx.ensures(...)` are prohibited
- [ ] Assertions on complex reports or structured objects where item order is unspecified or implementation-dependent (such as node execution sequences, collections of completed targets, or parallel wave results) verify set membership or set equality (e.g. `set(report.succeeded) == expected_set`) rather than enforcing strict list or tuple sequence equality unless sequence ordering is explicitly contracted
- [ ] Parity tests execute matching operations against both the real implementation and the fake, asserting identical return values and exception types
- [ ] Test methods in `Test<Target>ImplReal` are granular and single-concept, testing distinct error branches, precedence tiers, or algorithmic scenarios in dedicated test methods rather than clustering multiple subsystems into monolithic integration tests
- [ ] Tests respect static type contracts: passing `None` or invalid data types into parameters typed as non-optional is prohibited unless `Optional` or explicit runtime type validation is contracted in `low/<name>.pyi`
- [ ] Tests treat uncontracted failure conditions as undefined behavior: authoring tests for uncontracted non-concerns or asserting uncontracted defensive fallback outcomes is prohibited
- [ ] Assertions on error attributes verify only public domain entities contracted in the specification and never couple to internal graph placeholders or private implementation identifiers
- [ ] Intermediate representations and AST models favor flat standard data structures (such as lists of comparator tuples or dataclasses) over custom evaluation classes and stateful cache dictionaries
- [ ] Timeouts and delays use fast sub-second intervals (`0.01` to `0.05`s) or mocked time functions; multi-second sleeps are prohibited

## Hypothesis fuzz testing

- [ ] Fuzz testing is compiled via `compile_hypothesis_test_case(proto=proto, sut_factory=make_sut, initial_state_factory=<Target>State, name="<Target>FuzzTest")` or defined under `Test<Target>Fuzz`
- [ ] `sut_factory` supplies a cleanly initialized real target instance (with lifecycle phase scope entered if applicable)
- [ ] For modules exposing multiple singleton services, `sut_factory` supplies an aggregate SUT class declaring class attribute `tier = system`, declaring typed instance attributes (`_services: tuple[Any, ...]`), initializing member services inside an active phase scope into `self.__dict__["_services"]`, and delegating method lookup across constituent services in `__getattr__`
- [ ] In multi-singleton aggregate SUT classes, `__getattr__` ignores dunder lookups (`if name.startswith('__'): raise AttributeError(name)`) and inspects `self.__dict__.get("_services", ())` to avoid infinite recursion or attribute errors during caller tier introspection
- [ ] `initial_state_factory` returns a fresh model state dataclass instance
- [ ] Property fuzzing verifies invariant preservation and output equivalence between the real implementation and model transitions across pseudo-random action sequences
- [ ] Fuzz tests complete within bounded test budgets (default `--max-examples 50`) without indefinite loops or hangs; while loops in target methods implement progress checks or break conditions when no executable work items remain to prevent infinite busy-loops
