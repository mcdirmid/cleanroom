# benchmark interface component

## Purpose

The benchmark interface component defines model efficiency evaluation, financial rate computation, telemetry harvesting, and empirical verification reporting across model tiers and benchmark suites.

Evaluating language models across agentic development tasks requires standardized measurement of token efficiency, context caching ratios, step latencies, and financial costs alongside deterministic verification outcomes. Without uniform empirical definitions, cross-model comparisons suffer from inconsistent token accounting, hidden reasoning token omissions, and unverified code artifacts. The benchmark interface component provides canonical data representations for model capabilities, benchmark units, execution telemetry, and verification results, defining the contract for model efficiency assessment.

**Out of scope:** The benchmark interface component does not transmit network requests, spawn external subprocesses, or parse filesystem logs; these are handled by other components.

## Types and Behavior

A *model specification* describes an evaluated language model, carrying an *identifier*, a *tier number*, a *tier label*, a *provider name*, an *uncached input rate*, a *cached input rate*, an *output rate*, an optional *endpoint*, an optional *quantization*, and a *default harness*. The model specification computes a *financial cost* from non-cached inbound tokens, cached inbound tokens, and outbound tokens according to its rate card.

A *benchmark unit* identifies an evaluation target, carrying a *suite name*, a *task identifier*, a *unit directory*, a *target address*, and optional metadata (*archetype description*, *specification line count*, *target library line count*, and *description*).

A *flight telemetry* record captures operational metrics from an evaluation run, carrying *non-cached inbound tokens*, *cached inbound tokens*, *outbound tokens*, *total tokens*, financial cost, *step latencies*, *wall clock seconds*, and *role execution rounds*. Role execution rounds map role short names to execution round counts tallied during flight cleaning, where a round represents a Cleanroom role dispatch pass across targets until termination, encompassing all model steps executed within that pass.

A *verification outcome* record summarizes quality gates for a completed flight, carrying a *specification linter pass* status, a *type error count*, a *unit tests passed* count, a *unit tests failed* count, a *line coverage percentage*, a *branch coverage percentage*, a *mutation score percentage*, and a *convergence status*.

A *flight trace* records the complete empirical outcome of an evaluation run, carrying a *flight identifier*, an *ISO timestamp*, a *research question tag*, a model specification dictionary, a benchmark unit dictionary, a *methodology name*, *stages executed*, a flight telemetry record, and a verification outcome record.

A system's *benchmark evaluator* coordinates benchmark flight execution across model specifications and benchmark units under Cleanroom multi-role methodology or traditional single-agent baseline methodology, provides model and suite catalogs mapping identifiers to specifications and units, provisions ephemeral flight scope directories preserving the package structure of the benchmark unit's enclosing scope to isolate role workspaces and prevent concurrent flight collisions, marks specifications clean up to specification QA within the flight scope to isolate code and test generation, executes flights with optional custom results directory destinations, evaluates verification gates, archives synthesized library, test, and Cleanroom event log artifacts into sequential run files embedding flight telemetry metrics exclusively for successful flights that pass verification gates and achieve clean DAG convergence (where execution return code is zero and convergence status is true), drains benchmark unit directories and tears down ephemeral flight scopes and provisioned role workspaces upon flight completion (safely removing the flight scope and workspaces for successful flights, but preserving the flight scope directory as `<flight_scope>.failed` along with associated role workspaces under `<flight_scope>.failed/role_workspaces` for failed flights), and produces flight traces and formatted summary reports highlighting pass and fail status indicators alongside verification outcomes, returning a non-zero exit code from the command-line interface when any flight fails verification or execution. When pretense evaluation is requested, the evaluator coordinates synthesis and verification using Pretense state machines, synthesized fakes, deterministic unit tests, and property fuzzing across pretense roles or baseline prompts instead of the standard unit test and qa pipeline, evaluates verification gates against pretense test execution and statement coverage, and records the methodology as pretense. When baseline evaluation is requested, the evaluator provisions companion implementation guides (`guides/low_to_lib.md` and either `guides/pretense.md` or `guides/low_to_test.md`) into the flight scope directory, provides the target's low-level specification, and dispatches an autonomous software development agent instructed to consult the low-level specification (`low/*.pyi`), implement the two-file library structure in `lib/` matching the interfaces and implementation classes of the low-level specifications while consulting `guides/low_to_lib.md` for singleton lifecycle conventions, author unit tests in `tests/` (consulting `guides/low_to_test.md`) or pretense suites in `pretense/` (consulting `guides/pretense.md`), and verify code with type checking and 100% test coverage (annotating legitimately unreachable code with coverage opt-outs), equipped with standard development tools (terminal command execution, file viewing/reading, and file writing/editing) for exactly one agent round within the ephemeral flight scope to implement the library, author unit tests (or pretense suites), and execute verification without Cleanroom role micro-tools, strictly disallowing the deterministic loop harness, harvesting identical empirical telemetry with exactly one baseline role round, evaluating identical verification gates, and recording the methodology as baseline (or pretense-baseline when combined with pretense). When both baseline and pretense evaluation are requested, the evaluator provisions the runtime `pretense` package and companion guide (`guides/pretense.md`) into the baseline workspace root, pre-scaffolds the starter pretense suite from the low-level specification stubs, instructs the baseline developer to implement the library (consulting `guides/low_to_lib.md`) and author the state machine model, transitions, fake synthesis, unit tests, and property fuzz tests in `pretense/` rather than `tests/`, evaluates verification gates using Pretense test verification and statement coverage, archives results under `<model>+<harness>-pretense-baseline`, and records the methodology as `pretense_baseline`.

The component maintains a canonical *suite catalog* mapping suite identifiers—derived from the constituent part directories in benchmark parts (such as dag_engine, dag_engine_lite, and semver_solver)—to sequences of benchmark units, and provides *log harvesting* to extract empirical token usage, step latencies, and execution round counts from Cleanroom execution logs and subagent session transcripts.
